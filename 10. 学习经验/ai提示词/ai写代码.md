顶部标识：方法 ④
主标题：训练接口契约：锁定组件连接点
说明文字：既然模块拆开了！那么这两个部分互相传的接口参数、JSON，必须提前盖棺定论！
左侧模块
向 AI 下发模型 Schema
例如 User 有哪些字段？订单状态机怎么流转？在代码开发前，这些 Type/Schema 必须写死确认。
Mock 数据并行开发
用约定好的 Schema 让 AI 生成 Mock 假数据，前后端同时开工互不阻塞，最后联调无缝对接。
右侧模块
锁定 API 接口契约
只要接口契约雷打不动，不管内部逻辑经过 AI 怎么重构，都不会破坏系统整体联调。
把这当成防弹衣
代码写完，让 AI 留下一份傻瓜式的 README 说明。下个月的你，会感谢现在的自己。
第二张图片文字提取
先把模块之间的对接规范写好——谁发什么数据、格式是什么、返回图什么
第三张图片文字提取
把编码规范、架构要求、测试标准





模块 ①：不依赖 AI 盲找，先定层级
出红错不要复制整页死给 AI。先定性：它是表现层的传参挂了？还是持久层的 Schema 崩了？
底部提示：「分析此错：属于 MVC 中的哪一层？锁定层级后禁止超纲。」
模块 ②：顺着时序流排查断链
Payload 数据包从按钮点击开始，在哪个节点凭空蒸发了？这是工程师必须要做的抓虫破案盘道！
底部提示：「追踪数据流！从触发至此路由的链路中，哪个变量变成 undefined 了？找出来。」
模块 ③：沙箱文件内精准修复
绝对防线：不要让 AI 为了修一个 Bug 强行干预其它老代码！必须隔离报错的单体沙箱重写。
底部提示：「就在产生报错的单个文件内实现修补！绝不允许你跨文件修改任何底层组件和业务类！」
