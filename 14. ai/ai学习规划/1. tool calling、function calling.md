## 学习输出

为什么出现了这个tool calling？？它其实就是function calling

在此之前，只有llm，它的作用是用户问啥它打啥，只是一个单纯的一问一答的工具 

如果用户问当前北京天气怎么样，大模型就不知道当前北京天气怎么样，因为它只能回答它已知的内容，由于实时的天气是它不知道的，所以它只能回答它不知道。


但是如果有了tool，这个tool的作用就是，可以给llm调用的工具，有了这个工具，你再问llm现在北京天气怎么样，那么它发现可以通过调用一个‘get_weather()’的tool，就能回答用户的问题，于是它就会自主决策去调用这个工具，整理好调用这个 tool 需要传递的参数，比如参数是 { city: "北京" }，大模型输出这个格式的数据

但需要注意的地方是，不是大模型去真正调用这个get_weather函数，而是大模型知道有这个tool，并且它知道这个tool是用来查询天气的，还知道调用这个tool需要传的参数是什么，于是大模型输出调用这个tool的参数，然后通过代码或agent框架来去真正执行这个tool，也就是这个get_weather函数



因此这个function call解决的实际问题其实就是：
1. 大模型不知道的实时信息。如：天气、新闻、订单状态等
2. 大模型不能操作外部世界。如：发邮件、查数据库、查天气、修改文件，大模型可以将这些动作交给tool来做
3. 输出不可控。自然语言很难被程序去执行，而tool要求模型输出json参数，方便程序去执行和处理。


举个例子：

假设有一个getWeather函数，它的作用就是，调用三方获取天气的api，来获取某个城市当前的天气状况
```ts
function getWeather(city: string) {
  return fetch(`https://weather-api.com?city=${city}`)
}
```

于是你就把这个函数这样描述给llm：

```json
{
  "name": "get_weather",
  "description": "查询某个城市的实时天气",
  "parameters": {
    "type": "object",
    "properties": {
      "city": {
        "type": "string",
        "description": "城市名称"
      }
    },
    "required": ["city"]
  }
}
```


用户问：“现在北京天气怎么样”

llm可能不会直接回答，而是返回：
```json
{
  "name": "get_weather",
  "arguments": {
    "city": "北京"
  }
}
```

在程序根据大模型输出的工具的名称get_weather,找到了可执行的getWeather函数
程序执行getWeather("北京"),产生了这样的结果：
```json
{
  "city": "北京",
  "weather": "小雨",
  "temperature": "18°C",
  "wind": "3级"
}
```

程序将这个结果返回给llm
llm知道这些信息后，结合用户的问题，最终返回给用户：“北京今天有小雨，气温 18°C，风力不大。可以出门，但建议带伞。”

本质就是让llm生成结构化的json数据，程序来执行

这就是function call， 后来tool就不一定只是函数，还可以是：
- Web Search
- File Search
- Computer Use
- Database Query
- MCP Tool
- Browser Tool

可能会遇到的相关的工程问题：

1. 大模型给的参数就一定是正确的吗？
为了防止大模型给的参数可能是错误的，在调用工具之前，需要做参数校验

- 参数校验：
	1. schema
	2. 类型校验
	3. 必填字段校验

2. 大模型需要具备所有权限吗

为了防止大模型随便删文件、查隐私数据，我们需要给工具分权限，比如：
- 只读工具
- 写入工具
- 高风险工具
- 需用户确认的工具


3. 工具调用失败了怎么办

为了防止工具调用失败，我们需要做一层兜底，也就是错误处理
加入工具调用失败，程序可以告诉用户，如网络失败、文件不存在、请求超时等

4. 工具描述不清晰

为了防止工具描述不清晰，导致大模型该调的工具没有调，我们需要写清楚工具的作用和边界

5. 有太多的工具

如果有很多的tool一下子告诉llm，大模型在选择时就会变差，可以根据特定的任务场景，暴漏必要的工具

6. 工具调用结果要简洁

如果工具调用的结果有很多内容，如果全部喂给llm，模型上下文容易爆炸，因此工具调用的结果要简洁

7. 日志追踪

记录：
- 模型为什么调用工具
- 调用了什么工具
- 参数是什么
- 调用结果是什么
- 调用成功还是  失败
- 花了多少token和时间
