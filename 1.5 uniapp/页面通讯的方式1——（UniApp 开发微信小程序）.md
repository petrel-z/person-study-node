### 1. 路由参数传递
| 维度       | 说明                                                                                                                                                                                                   |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **原理**   | 通过路由跳转 URL 的查询字符串（`?key=value`）携带数据，本质是 URL 参数传递。                                                                                                                                                    |
| **使用方式** | 1. 跳转时在 `url` 中拼接参数：<br>   `uni.navigateTo({ url: '/pages/B/B?id=1&name=test' })` <br> 2. 目标页面在 `onLoad` 生命周期中通过 `query` 参数接收：<br>   `onLoad((query) => { console.log(query.id) })`（参数为字符串类型，需手动转换）。 |
| **应用场景** | 简单数据传递（如 ID、名称等），适合页面跳转时一次性传递少量数据，且无需后续交互。                                                                                                                                                           |
#### 注意事项：
- **数据类型限制**：参数仅支持字符串类型，数字 / 布尔值需手动转换（如 `Number(query.id)`），否则可能因类型错误导致逻辑异常（如 `'1' == 1` 成立但 `'1' === 1` 不成立）。
- **长度限制**：URL 总长度有限制（通常 2KB~10KB，不同平台有差异），**禁止传递大型对象或长文本**（如 JSON 字符串化的表单数据），否则会被截断导致数据丢失。
- **安全性**：参数会暴露在 URL 中，敏感信息（如 token、密码）绝对不能通过路由参数传递，需用 storage 或 store 替代。
- **适用跳转方式**：`navigateTo`/`redirectTo` 支持参数传递，但 `switchTab` 跳转时参数会被忽略（需用其他方式传递）。

### 2. 全局状态管理（Pinia/Vuex）
| 维度       | 说明                                                                                                                                                                                                                                                     |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **原理**   | 通过全局共享的状态容器存储数据，所有页面/组件可直接读写容器中的数据，数据变更时自动响应。                                                                                                                                                                                                          |
| **使用方式** | 以 Pinia 为例：<br> 1. 定义 Store：<br>   `export const useStore = defineStore('id', { state: () => ({ count: 0 }), actions: { increment() { this.count++ } })` <br> 2. 页面中使用：<br>   `const store = useStore(); store.increment(); console.log(store.count)`。 |
| **应用场景** | 多页面/组件需要共享数据（如用户信息、全局配置），或频繁交互、跨层级通信（如购物车数量、主题切换）。                                                                                                                                                                                                     |
#### 注意事项：
- **响应式规范**：修改状态必须通过 `actions`（Pinia）或 `mutations`（Vuex），禁止直接修改 `state`（如 `store.count++`），否则可能导致数据更新但视图不刷新（Vue3 响应式跟踪依赖于正确的修改方式）。
- **模块拆分**：避免单一大 Store，按业务拆分模块（如 `userStore`、`cartStore`），防止状态混乱难以维护。
- **持久化处理**：Pinia/Vuex 状态默认在页面刷新后丢失，需结合 `uni.setStorageSync` 手动持久化（如登录状态：`actions` 中修改状态后同步存储到本地）。
- **性能优化**：频繁变更的状态（如滚动位置）不宜放入 Store，避免不必要的响应式开销，可用本地变量或 `ref` 单独管理。

### 3. 本地存储（Storage）
| 维度       | 说明                                                                                                                                                  |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| **原理**   | 利用微信小程序的本地存储 API（同步/异步）将数据持久化到本地文件系统，实现跨会话数据共享。                                                                                                     |
| **使用方式** | 1. 存储：`uni.setStorageSync('user', { name: '张三' })` <br> 2. 读取：`const user = uni.getStorageSync('user')` <br> 3. 移除：`uni.removeStorageSync('user')`。 |
| **应用场景** | 需要持久化保存的数据（如登录令牌、用户偏好设置），或跨页面共享且不频繁变更的数据（如历史记录）。                                                                                                    |
#### 注意事项：
- **容量限制**：微信小程序单个 key 存储数据不超过 1MB，总容量通常 10MB 左右，**避免存储过大数据**（如 base64 图片），否则可能导致存储失败或性能下降。
- **数据类型转换**：`setStorageSync` 会自动将数据 JSON 序列化，读取时需注意类型还原（如日期对象会被转为字符串，需重新实例化）。
- **时效性**：存储的数据不会自动过期，需手动管理生命周期（如登录 token 过期后需及时删除，避免使用失效数据）。
- **跨端差异**：H5 环境下 `localStorage` 遵循同源策略，而小程序端无此限制，但不同端的存储 API 行为可能有细微差异（如同步 / 异步的执行时机），需做好兼容测试。

### 4. 事件总线（EventBus，基于 mitt）
| 维度         | 说明                                                                 |
|--------------|----------------------------------------------------------------------|
| **原理**     | 基于发布-订阅模式，通过全局事件中心注册事件（订阅）和触发事件（发布），实现无直接关联页面/组件的通信。 |
| **使用方式** | 1. 定义事件总线：`import mitt from 'mitt'; export const bus = mitt()` <br> 2. 页面A发布：`bus.emit('eventName', data)` <br> 3. 页面B订阅（需在 `onUnload` 中取消）：<br>   `bus.on('eventName', (data) => { ... }); onUnload(() => bus.off('eventName'))`。 |
| **应用场景** | 非父子关系页面的轻量通信（如跨页面通知刷新、状态变更），适合临时、低耦合的交互。 |
#### 注意事项：
- **内存泄漏风险**：页面卸载前必须移除事件监听（`bus.off`），否则已销毁的页面仍会接收事件，导致内存占用增加甚至逻辑错乱（如重复请求接口）。
- **事件名冲突**：全局事件需规范命名（如 `prefix:eventName`，如 `user:login`），避免不同业务模块的事件名重复，导致意外触发。
- **数据溯源困难**：事件流是隐式的，复杂场景下难以追踪数据传递路径，调试难度高于 Store 或事件通道，**不建议用于核心业务流程**。

### 5. 事件通道（getOpenerEventChannel）
| 维度       | 说明                                                                                                                                                                                                                                                                                                                                            |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **原理**   | 微信小程序官方提供的页面栈内通信机制，通过 `navigateTo` 打开页面时创建专属事件通道，支持父子页面双向通信。                                                                                                                                                                                                                                                                                  |
| **使用方式** | 1. 父页面跳转时定义接收事件：<br>```ts<br>uni.navigateTo({ <br>url: '/pages/child', <br>events: { childMsg: (data) => {} }, <br>success: (res) => res.eventChannel.emit('parentMsg', data) })<br>```<br>   <br> 2. 子页面获取通道并通信：<br>   `const channel = uni.getOpenerEventChannel(); channel.on('parentMsg', (data) => {}); channel.emit('childMsg', data)`。 |
| **应用场景** | 父子页面（非 tabBar 页）的双向交互（如子页面回传表单数据、父页面向子页面发送实时指令）。                                                                                                                                                                                                                                                                                              |
#### 注意事项：
- **跳转方式限制**：仅支持 `uni.navigateTo` 打开的非 tabBar 页面，`switchTab`（跳 tab 页）、`reLaunch`（关闭所有页面打开新页）、`redirectTo`（关闭当前页打开新页）均不创建事件通道，调用 `getOpenerEventChannel` 会返回 `undefined`。
- **跨端兼容性**：H5 环境下可能不支持（或行为不一致），需用类型守卫判断（如 `if (typeof getOpenerEventChannel === 'function')`），并搭配路由参数或 storage 作为降级方案（如你在分类页中的处理）。
- **通信时机**：子页面发送事件前需确保父页面已完成事件注册，建议在父页面 `success` 回调中确认页面打开后再发送初始化数据，避免子页面先发事件但父页面未监听的情况。
- **数据体积**：虽然比路由参数灵活，但仍不建议传递过大数据（如超过 100KB），可能导致通信延迟或小程序卡顿。

### 6. 页面栈操作（getCurrentPages）
| 维度       | 说明                                                                                                                                                                 |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **原理**   | 通过 `getCurrentPages()` 获取当前页面栈数组，直接访问前序页面实例，修改其数据或调用方法。                                                                                                            |
| **使用方式** | 1. 子页面中获取父页面实例：<br>   `const pages = getCurrentPages(); const prevPage = pages[pages.length - 2]` <br> 2. 操作父页面：`prevPage.$vm.data = '新值'; prevPage.$vm.method()`。 |
| **应用场景** | 紧急情况下的简单通信（不推荐常规使用），仅适用于非 tabBar 页面，且需确保页面栈存在。                                                                                                                     |
#### 注意事项：
- **强耦合风险**：直接操作前序页面实例（如 `prevPage.$vm.data = xxx`）会导致页面间依赖紧密，若前序页面修改了数据结构或方法名，子页面会直接报错，维护成本高，**非紧急情况禁止使用**。
- **页面栈稳定性**：页面栈长度可能因用户操作（如 `navigateBack` 多步）或小程序限制（通常最多 10 层）发生变化，直接通过索引（`pages.length - 2`）获取前序页面可能导致数组越界，需先判断长度（如 `if (pages.length >= 2)`）。
- **仅支持非 tab 页**：tabBar 页面不会加入页面栈，通过 `switchTab` 打开的页面无法通过页面栈获取，调用会返回错误实例。

### 7. 依赖注入（Provide/Inject）
| 维度         | 说明                                                                 |
|--------------|----------------------------------------------------------------------|
| **原理**     | Vue3 原生 API，通过父页面（或根组件）`provide` 提供数据，子页面（或深层组件）`inject` 注入数据，基于组件树传递。 |
| **使用方式** | 1. 父页面提供：`import { provide } from 'vue'; provide('key', value)` <br> 2. 子页面注入：`import { inject } from 'vue'; const value = inject('key', defaultValue)`。 |
| **应用场景** | 页面嵌套层级较深时（如父页面 → 子组件 → 孙页面）的数据传递，避免 props 逐层透传。 |
#### 注意事项：
- **类型提示缺失**：TS 环境下 `inject` 无法自动推断类型，需显式声明类型（如 `inject<Type>('key', defaultValue)`），否则可能因类型错误导致逻辑问题。
- **数据来源模糊**：深层页面难以追溯 `provide` 的源头，不适合核心数据传递，建议仅用于次要配置（如主题、语言）。
- **响应式限制**：若传递的是普通值（非 `ref`/`reactive`），修改后不会触发注入页面的更新，需确保传递响应式数据（如 `provide('count', ref(0))`）。

### 选择建议：
- 简单跳转传参 → 路由参数  
- 多页面共享数据 → Pinia  
- 持久化数据 → 本地存储  
- 父子页面双向交互 → 事件通道  
- 跨页面轻量通知 → 事件总线  
- 深层嵌套传递 → 依赖注入  
- 避免频繁使用页面栈操作（耦合度高）。


### 通用注意事项：
- **单一数据源原则**：同一数据（如用户选择的分类）不要同时用多种方式传递（如既存 Store 又通过事件通道回传），避免状态不一致（如一处更新后另一处未同步）。
- **页面生命周期配合**：需要在页面显示时刷新的数据（如从详情页返回列表页后刷新列表），需在 `onShow` 中处理（而非 `onLoad`，`onLoad` 仅触发一次），结合 Store 或 storage 读取最新数据。
- **错误处理**：所有通信方式都需考虑异常情况（如参数缺失、事件未监听），添加兜底逻辑（如 `const id = query.id || ''`、`eventChannel?.emit(...)` 用可选链避免报错）。
