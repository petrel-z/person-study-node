浏览器的架构模式
1. 只有一个进程，不同任务分配不同的线程
	1. 优点：适合小型应用，模型简单，易实现
	2. 缺点：一个地方出问题，整个应用都会被影响
2. 有多个进程，不同进程处理不同的任务
	1. 优点：一个地方出问题，只会局部影响应用，不会涉及整个应用
	2. 缺点：模型复杂，不易实现

浏览器多进程的好处：
每个进程负责不同的任务，不会出现，当一个进程负责的任务卡死，影响其他任务的执行

站点隔离：
是浏览器的一种安全机制，本质是为了防止不同网站恶意互相访问数据，不同网站分配不同的内存进程
它是一种在操作系统层面的隔离，阻断了内存的中的数据访问

同一个网站内可能会应用其他网站的资源，如iframe内嵌其他网站的内容
此时就会通过站点隔离，如果iframe与本网站不同源，就进行站点隔离，不共享进程中的内存；
如果iframe与本网站同源，则可以是同一个进程，并共享内存。

# 用户输入url后页面是怎么加载的（线程方面）

浏览器的url输入框不仅用来url跳转，还用来充当搜索引擎进行搜索
当用户输入一个url时，按下了enter键后
1. 浏览器的ui线程就会用当前url发送一个请求，发送完毕后就将网络请求交给网络线程。
	同时，一个旋转加载中的图标会充当tab标签页中的favicon图标	
	网络线程可能会收到请求返回的http301重定向信号，此时它就会通知ui线程，你再根据这个重定向的url再发送一次请求，这时ui线程就会根据新的url发送一个新的请求
2.  请求返回响应体后，网络线程会利用MIME Type sniffing来知道所返回的数据到底是什么样的数据，避免content-type字段的信息的缺少或者错误，从而避免浏览器展示错误的信息
3. 当网络线程确定了返回的响应数据是html后，就将数据交给渲染进程
4. 当网络线程检查完毕后，确认返回的数据是正确且安全的，将会告诉ui线程，“我已完成任务”，随后ui线程会找一个渲染进程，来进行页面的渲染
	1. 由于网络请求花费的事件在百毫秒，那该怎么优化这个过程呢？

答案就是：当ui线程第二次发送请求，并等待网络线程检查响应数据过程中，ui线程会准备好渲染进程，当网络线程那边没问题了，通知ui线程后，这个渲染进程直接进行渲染
另外一种情况是，如果返回的是跨站跳转，则就需要另一个渲染进程了。

5. 最后一步，浏览器进程会通过IPC将数据持续不断的传递给渲染进程，渲染进程确认数据接收完毕后，会告知浏览器进程。此时这次导航完成。
	导航完成后：
		地址栏会显示更新
		浏览器告知ui线程，ui线程会将加载的图标换成新页面的favicon图标，


## service worker
它是一个运行在后台的独立的浏览器线程的脚本，本质是一种特殊的 Web Worker，主要用于实现**离线缓存、后台同步、消息推送**等高级功能，是 Progressive Web App（PWA）的核心技术之一。


### 核心特性
1. 独立运行
	1. 独立于浏览器主线程，当页面关闭时，该线程仍可在后台运行
2. 拦截网络请求
	1. 可拦截页面发送的所有请求（fetch、XMLHttpRequest等），还可自定义响应策略（返回缓存数据还是网络数据）
3. 持久化缓存
	1. 借助CacheStorage api可实现对js、图片、css、接口数据等资源的持久化存储，声明周期由开发者控制，且独立于其他浏览器缓存
4. 事件驱动
	1. 通过事件触发自身工作。register、install 、activate、fetch、push

### 实现流程
1. 注册**Register**
2. 安装**install**
3. 激活**activate**
4. 运行**fetch/message**

详细代码
```js
// 注册
if ('serviceWorker' in navigator) {
  window.addEventListener('load', () => {
    navigator.serviceWorker.register('/sw.js') // 注册指定路径的 Service Worker 脚本
      .then(registration => {
        console.log('注册成功：', registration.scope);
      })
      .catch(err => {
        console.log('注册失败：', err);
      });
  });
}
// 1. - `scope`：Service Worker 控制的范围（默认是脚本所在目录及子目录），超出范围的页面不会被其拦截。

// 安装
// sw.js
const CACHE_NAME = 'my-cache-v1';
const PRECACHE_RESOURCES = ['/', '/index.css', '/app.js'];

self.addEventListener('install', (event) => {
  // 等待缓存完成后再结束 install 阶段
  event.waitUntil(
    caches.open(CACHE_NAME)
      .then(cache => cache.addAll(PRECACHE_RESOURCES))
      .then(() => self.skipWaiting()) // 跳过等待，直接激活新的 Service Worker
  );
});

// 激活
self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then(cacheNames => {
      return Promise.all(
        cacheNames.filter(name => name !== CACHE_NAME)
          .map(name => caches.delete(name)) // 删除旧缓存
      );
    }).then(() => self.clients.claim()) // 立即控制所有打开的页面
  );
});
// 常用与删除旧缓存

// 运行
// 开始监听页面请求，监听fetch事件或消息（message事件）
self.addEventListener('fetch', (event) => {
  // 缓存优先策略：先读缓存，缓存没有再请求网络
  event.respondWith(
    caches.match(event.request)
      .then(cachedResponse => {
        // 缓存存在则返回，同时后台请求网络更新缓存
        const fetchPromise = fetch(event.request).then(networkResponse => {
          caches.open(CACHE_NAME).then(cache => {
            cache.put(event.request, networkResponse.clone());
          });
          return networkResponse;
        });
        return cachedResponse || fetchPromise; // 缓存优先，否则用网络
      })
  );
});
// 接收页面消息
self.addEventListener('message', (event) => {
  console.log('收到页面消息：', event.data);
  // 可通过 event.source.postMessage() 向页面发送消息
});
```

### 生命周期
1. 安装
2. 激活
3. 运行（Idle/Waiting）：监听网络请求
4. 更新：service worker脚本发生变化，触发更新，重新安装-激活，替换旧版本

### 可实现的高级功能：
1. 离线缓存：
	当用户断网后，仍然能够打开网页。是因为用户在第一次打开网页的时候，将网页缓存在了service worker中，断网后仍能打开。
2. 后台同步：
	当用户在提交表单时断网，service worker它会
	1. 帮用户暂存表单信息
	2. 联网时，自动帮用户提交表单
3. 消息推送：
	当断网时，service worker仍能

### 总结
1. 独立：拥有自己的生命周期

## 渲染进程

渲染进程拿到IPC传输过来的数据，开始边接收数据边解析
- 他会先构建DOM树，除了html资源，还有js、css资源
	在解析html时，遇到其他资源时，会停下手中的解析，先去下载其他资源
	这样就会导致解析特别慢，因此提出了 preload scanner 来处理子资源的请求
	preload scanner 下载资源和渲染进程解析html会同步进行

- 由于js拥有类似于document.write()的方法可以修改DOM元素，因此处理js的优先级比html高，有js出现，html就会被暂停解析，直到js代码执行完毕
	若给js加上async 或 defer
		async：js解析与html解析同步进行，js下载完毕后，会暂停html解析，去执行js
		defer：js解析与html解析同步进行，但是会等到html解析完毕后执行js

- dom树构建完成后，渲染进程根据css选择器，将样式添加到每个dom节点元素上渲染进程
- 布局：渲染进程计算每个节点的位置，并生成布局树（Layout Tree）
	布局树会保留所有实际参与了布局的元素，不保留实际没有参与布局的元素
	因此`visible: hidden` 会参与布局 ，display：none 不会参与布局
- 下一步就是进行绘制
	浏览器主线程遍历布局树，生成绘制记录（Paint records），记录谁在上，谁在下。
- 下一步就是合成
	以前的技术：根据dom树、css样式、layout 树、Paint records等信息，将这些信息转化为像素点铺在屏幕上，这就是光栅化（rasterizing）
		页面滚动会引起光栅化新的部分，已过时
	现在的技术：合成
		独立部分分配在独立的layer中，再又独立的合成线程将独立的layer光栅化，最后缓存下来，将所有缓存的内容合成成一个完整的网页。就不会出现滚动时需要重新光栅化了。
	问题：元素如何被划分到不同的layer上
		通过遍历Layout tree ，并计算元素的层级关系，从而划分到不同的layer上。
总结：
1. html解析和样式计算
2. 布局
3. 绘制
4. 合成

如果dom元素改变了呢？该从哪一步开始重新进行
从布局开始
